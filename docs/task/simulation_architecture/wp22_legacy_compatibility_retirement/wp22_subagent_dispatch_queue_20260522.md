## Worker Return Packet

Every worker must return:

- status: `pass`, `blocked`, `partial`, `timeout`, or `preflight-only`;
- touched files;
- validation commands and outcomes;
- remaining legacy paths;
- blockers and the failing guard that exposes each blocker;
- integration notes for the next stream;
- confirmation that unrelated edits were not reverted.

## Return Packet Completeness Gate

A worker return packet is complete only when it covers every required field
listed above and the stream-specific dispatch packet. Thread closure alone is
not evidence of completion.

Status meanings for this queue:

- `pass`: the packet is complete, all required fields are present, and no named
  blocker remains. A `pass` packet may authorize the next implementation step,
  but it does not bypass later closure or acceptance lanes.
- `blocked`: the worker identified a named blocker. The packet is complete
  enough to explain the failure, but the downstream stream remains blocked
  until the blocker has an owner, replacement, and failing guard.
- `partial`: the worker returned some evidence, but the packet is incomplete or
  the scope was only partly covered. `partial` never unlocks downstream
  implementation or acceptance.
- `timeout`: the worker stopped before returning a complete packet. Record the
  stream as `timeout` or `blocked` as appropriate, but never treat the closed
  thread as proof of completion. `timeout` never unlocks downstream
  implementation or acceptance.
- `preflight-only`: the worker was limited to read-only verification or scope
  discovery. It may recommend the next step, but it does not authorize
  implementation or acceptance by itself.

Rules:

- Only a complete `pass` packet can be consumed as readiness evidence for the
  next stream.
- `partial`, `timeout`, and `preflight-only` are not substitute completion
  states.
- Closing a worker thread is a transport event, not a completion event.
- A closed thread never unlocks downstream readiness or acceptance.
