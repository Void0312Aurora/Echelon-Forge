## 1. 源论点

temp-02 认为当前架构正确解决了“如何执行世界”（通过生命周期 + DAG + 契约），但尚未定义其最高抽象。项目天花板由 Echelon-Forge 最终成为何种系统决定，而非其调度执行节点的整洁程度。

核心重构：**DAG 是一个投影，而非本体论。** 真正的目标是统一语义、因果、时间、信息、智能、学习和证据的平台——一个“仿真编译器 + 学习平台”，而不仅仅是“运行时引擎”。

## 2. 需吸收的内容

### 2.1 SCAL 作为架构愿景

temp-02 提出了 SCAL（语义-因果-智能-学习）作为四面架构框架。这是对架构基线已零散解决的方面的恰当命名：

| SCAL 面 | 回答什么问题 | 当前架构覆盖 | 差距 |
|---------|-------------|-------------|------|
| **语义** | 世界中存在什么？实体、能力、任务、约束、角色、事件。 | P0-P10 语义生命周期 + 9 个领域模型族（第8节）+ 契约分类（第7节） | 领域本体未形式化。以实体为中心而非以能力为中心。 |
| **因果** | 什么导致什么？哪些状态变更产生哪些后果？ | 跨层契约（第6节）+ 事件排序（第5节）+ WP2.5 调度器语义 | 因果图未显式建模。因果正确性未在运行时强制。 |
| **智能** | 谁决策？谁知道什么？谁控制什么？ | 策略/编排层（第6节）+ 指挥层级（P2-P4）+ ActionIntentPacket + CoordinationIntentPacket | 智能体 = 角色 + 权限 + 信息状态 + 决策模型 + 动作接口 未形式化。策略仍被当作整体对待。 |
| **学习** | 系统如何训练、评估、生成任务、发现失败、改进？ | 当前架构基线未覆盖。 | 完全缺失。课程、评估、能力画像、场景生成均推迟到 Python 脚本。 |

**建议**：采用 SCAL 作为架构愿景声明，替换当前架构基线的“设计论点”（第1节）。四个面成为架构文档的组织框架。学习是真正需要设计工作的新面。

### 2.2 图之图：DAG 是投影，而非本体论

temp-02 识别了仿真系统中共存的七个图。映射到当前架构：

| 图 | 当前状态 | 行动 |
|----|---------|------|
| **语义图** | 隐含在模型族 + P0-P10 中 | 显式化。这是 P0 ContentCompile 产生的。 |
| **因果图** | 隐含在跨层契约 + 事件排序中 | 显式化。WP2.5 屏障可见性是第一步。 |
| **时序执行图** | 时序 DAG（第5节）+ WP2.5 时钟域合并 | 已显式。这是当前架构最强的图。 |
| **信息图** | 隐含在传感器→航迹→数据链→观测链中 | 提升为一等公民。见下方 2.3 节。 |
| **智能图** | 隐含在策略/编排层 + 指挥层级中 | 显式化。见下方 2.4 节。 |
| **证据图** | DiagnosticsTrace + 验证门 + 重放契约 | 已有具体类型（DiagnosticsTrace）。用 WP2.5 重放契约扩展。 |
| **学习图** | 未覆盖 | 推迟。需独立架构文档。 |

**建议**：在架构基线中增加“图之图”章节，定位每个图，命名其所有者，并声明其与其他图的关系。时序 DAG 仍作为执行调度器；不再将其呈现为架构的定义性隐喻。

### 2.3 信息状态架构——可直接行动

这是 temp-02 最具直接可操作性的贡献。六层信息模型与现有基础设施清晰对应：

```
世界真相          → flecs::world 权威状态
感知状态          → ISensorModel::scan() → Detection / ContactList
航迹状态          → TrackDatabase → TrackData → TrackPacket
共享态势          → DataLinkSystem → 共享战术图景
智能体观测        → AgentObservation / ObservationPacket
决策信念          → [缺失——当前观测直接映射到动作]
```

当前架构有第1-5层。第6层（决策信念）是关键缺失部分——它的缺失导致 RL 策略可以学习“上帝视角”策略。引入显式信念层将：

1. 防止策略直接消耗世界真相。
2. 使部分可观测性、通信约束和传感器欺骗成为一等仿真特性。
3. 使信息退化（延迟、丢包、融合、推理）在架构上可见，而非埋藏在系统实现中。

**建议**：在架构基线中增加“信息状态架构”作为新章节。定义六层及其所有权和转换规则。使 `DecisionBelief` 成为 ObservationViewSpec 契约中的正式概念——观测是智能体看到的；信念是智能体认为是真的。

### 2.4 智能体模型——角色 + 权限 + 信息 + 决策 + 动作

temp-02 的智能体五层分解自然地映射到现有的 P2-P4 指挥层级：

```
战略/作战意图         → P2 TaskingIntent（TaskOrder, LeaderIntent）
战术条令               → DoctrineFamily（第8节）
平台自主性             → P4 PlatformControl
控制/自动驾驶          → P4 力/扭矩输出 → P5 PhysicsStep
策略网络               → 可在任意层插入
```

关键洞察：**RL 策略不是智能体。它是一个可替换的决策模型，插入到智能体层级的一个或多个层。** 五元素智能体定义（角色 + 权限 + 信息状态 + 决策模型 + 动作接口）应取代隐式的“智能体 = 神经策略”假设。

**建议**：在 WP4-D（策略与协调桥）中形式化智能体模型。定义 `AgentRole` 为契约类型，包含角色、权限范围、信息状态源、决策模型引用和动作接口等字段。这将支持未来的脚本化条令、基于规则的战术、RL 策略、LLM 规划器、MCTS 和人机回环——全部通过同一智能体接口。

### 2.5 能力图——平台 = 能力包

以实体为中心的模型（`spawn_unit("F-16C_Block50")`）是潜在的空/海/武器分化的根本原因。以能力为中心的模型将平台定义为组合：

```
平台 = 机动能力
     + 传感器能力
     + 通信能力
     + 发射器能力
     + 生存能力
     + 指挥能力
     + 条令轮廓
```

这是真正从架构上防止垂直堆栈的方法。新领域（地面、太空、潜艇）添加能力实现，而非新的运行时路径。

**建议**：在领域扩展模型（第8节）中添加能力组合概念。定义 `Capability` 为契约概念，具有类型化接口。保留当前 `spawn_unit(type_name)` 作为便利快捷方式，内部扩展为能力组合。长期目标是 `spawn_platform({capabilities...})` 作为规范创建路径。

### 2.6 仿真编译器——长期定位

编译流水线（场景 → 语义编译 → 因果依赖 → 时序调度 → 运行时 → 证据 → 学习）是正确的长期愿景。它将 Echelon-Forge 从“运行场景的仿真器”重构为“将任务语义编译为可执行、可解释、可比较实验的平台”。

这在当前的 WP0-WP5 阶段尚不可实施——编译器需要经过验证的运行时。但应作为项目的长期架构愿景加以阐述，以防止当前内核工作被误认为是最终架构。

**建议**：将“仿真编译器”添加为架构愿景声明。当前的 WP0-WP5 工作构建了编译器将目标指向的经验证运行时内核。

## 5. 架构愿景声明（提议）

将当前架构基线第1节（“设计论点”）替换为：

> Echelon-Forge 是一个**语义-因果仿真编译器与学习平台**。它将任务语义、领域模型、智能体结构及保真度要求编译为可执行、可解释、可回放、可比较的仿真实验。
>
> 架构围绕四个面组织：
>
> - **语义面** — 世界中存在什么。领域本体、能力图、场景与任务语义。
> - **因果面** — 什么导致什么。因果图、时序执行 DAG、事件模型、状态转换语义、反事实模型。
> - **智能体面** — 谁决策与行动。智能体角色模型、指挥层级、信息状态架构、决策分层、策略接口、条令模型。
> - **学习面** — 系统如何改进。课程架构、世界模型架构、评估架构、能力分析器、场景生成器。
>
> 时序 DAG 是因果面中的执行投影——它安排计算，但并非架构的定义性抽象。架构的天花板取决于这四个面如何融合为一个统一平台，而非 DAG 的实现有多清晰。

## 6. 结论

temp-02 是继调度器语义与外观对齐评审后的正确下一轮对话。它并非指出现有架构的缺口——而是指出，当前架构是一个更大系统（尚未命名）的内核。

最有价值的四项吸收点：

1. **SCAL** 作为组织框架——用四个面取代扁平的“设计论题”，每个面都有清晰的归属和交付物。
2. **信息状态架构**——六层模型可直接操作，并解决了 RL 质量最大的单一风险（上帝视角策略）。
3. **智能体 = 角色 + 权限 + 信息 + 决策 + 行动**——防止架构随着 RL 方法的演进而锁定在“智能体 = 神经策略”上。
4. **能力图**——真正从架构层面防止出现空中/海上/武器垂直堆栈。

SCAL 愿景并未使当前的 WP0-WP5 计划失效。它只是为那个计划赋予了名称和上限。
