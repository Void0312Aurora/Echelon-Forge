## 9. 对post_wp9的建议调整

### 9.1 添加到轨道1（因果运行时基础）

该轨道应显式交付：

1. **调度窗口循环骨架**——不是完整的多速率调度器，而是一个最小窗口循环，演示：收集外观请求 → input_injection屏障 → 运行无环DAG（来自清单） → window_commit屏障 → 导出屏障。这将四个原语（StateStore、EventQueue、Barrier、StageNodeManifest）连接为一个工作系统。

2. **同窗口边验证**——在调度构造时（非运行时），验证声明的边是否符合架构文档§7规则：B.read_set必须与A.write_set相交，并且A必须声明同窗口输出。

### 9.2 添加到轨道2（外观垂直切片）

该轨道应显式交付：

3. **`ActionHoldPolicy` DTO**——在切片能够演示策略→控制→物理节奏之前的前置条件。字段：`hold_last`、`interpolate`、`expiry`、`drop`，带有有效持续时间和刷新节奏。

4. **信息状态来源标签**——在现有的ObservationPacket元数据字段（WP9 DTO-3）上，演示快照携带标识其采样自哪个信息层的来源标签。

### 9.3 记录为延期（不在当前轨道中）

5. **GAP-5**（法则14执行）——需要读端AST分析或运行时守卫。延期至信息状态来源标签（GAP-4）存在之时。

6. **GAP-6**（Agency Graph运行时）——权限执行、基于角色的访问控制。延期至因果基础（轨道1）和外观切片（轨道2）稳定之时。

7. **GAP-7**（转换规则表面化）——延期至来源标签作为稳定词汇存在之时。

8. **GAP-9**（时钟域执行）——延期至窗口循环骨架（GAP-2）正常工作之时。清单注册表中的建议性时钟域是可接受的第一步。

## 10. 结论

post_wp9的五轨道路线在排序逻辑上是正确的。因果基础必须先行；能力组合和反事实工作不能在其之前。

然而，post_wp9对轨道1和轨道2为了将架构文档第7节和第8节变为现实所必须交付的内容描述不足。具体来说：

- **轨道1**拥有原语（StateStore、EventQueue、Barrier、Manifest），但没有将它们连接起来的**调度窗口循环**（GAP-2/GAP-3）。
- **轨道2**拥有外观导出路径，但没有**ActionHoldPolicy**（GAP-1）和**信息状态来源标签**（GAP-4）。

这四项不是架构发现。它们是对架构文档中已完全指定的需求的实现。将它们添加到轨道1和轨道2并不会扩大范围——它使现有范围精确到足以验证。
