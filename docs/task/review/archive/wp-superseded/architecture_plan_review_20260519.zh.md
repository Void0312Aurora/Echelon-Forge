## 1. 源论点

temp-01 认为架构计划“正确但过载”——它方向正确（统一生命周期、时序 DAG、外观契约、显式层耦合），但尚未收敛到最小、可冻结、可验证的架构内核。它识别出八项具体风险，并提出了一个重新排序的工作包结构。

本文档对照架构基线和 WP3 实现证据评估每项声明，然后记录哪些问题有效且可操作。

## 2. 逐声明评估

### 声明1：架构基线“关闭过早”

**源论点**：StateStore、EventQueue、ClockDomain 和 Barrier 语义尚未冻结，但架构文档宣称框架已关闭。这可能导致实现在局部重新解释。

**发现：部分有效，但关闭机制比声称的更细致。**

架构文档（第6节）定义了四级关闭模型：

- **A级**（框架形状）：已关闭 —— 层、层间关系、拥有/不得拥有、跨层通道均已命名。
- **B级**（契约语义）：当存在一条规则及至少一个具体示例时关闭。
- **C级**（实现对齐）：通过任务计划、迁移阶段、架构测试或 PR 关闭。
- **D级**（内部设计空白）：由单独的特定层架构文档关闭。

StateStore、EventQueue、ClockDomain 和 Barrier 执行语义属于 B 级，而非 A 级。架构文档明确说明“状态版本控制从粗粒度开始，但必须为分片留出空间”以及“时钟域默认使用嵌套触发”——这些是设计规则，而非冻结实现的声明。关闭规则包含一条停止规则：“在以上 B 级规则存在后，不应为同一框架发起 temp-04 类型的评审。新发现应作为直接 B 级补丁、C 级任务计划或 D 级特定层架构文档路由。”

**处理：已确认。关闭模型是充分的，但应在架构文档中更突出地说明 A 级框架关闭与 B 级语义冻结之间的区别。**

### 声明2：没有 StageNodeManifest，P0-P10 有成为“通用标签系统”的风险

**源论点**：没有机器可检查的清单，P0-P10 就会成为任何人都可以应用的标签，无法强制执行读/写/同步/延迟约束。

**发现：有效。正式的 StageNodeManifest 是连接架构文档和可验证代码之间的缺失环节。**

架构文档（第5节）已经要求每个阶段节点声明 `semantic_stage`、`read_set`、`write_set`、`clock_domain`、`latency_policy` 和 `sync_policy`。`exact_stage_inventory.cpp` 文件中有28个阶段描述符，包含 `reads`/`writes`/`depends_on_stages` 字段，但这些字段仅用于信息提供——没有调度器强制执行它们。

建议的清单模式（15个字段，包括 `input_packets`、`output_packets`、`read_state_shards`、`write_state_shards`、`read_snapshot_policy`、`write_commit_policy`、`allowed_same_window_edges`、`required_barriers`、`event_families_emitted`、`diagnostic_trace_obligations`、`facade_visibility`、`compatibility_adapter_allowed`）是对架构文档要求的6字段模式的合理细化。

**处理：已接受。StageNodeManifest 应成为 WP2 或 WP2.5 的交付物，最初为 markdown 模式，后续为机器可读格式。**

### 声明3：WP2 契约冻结与 WP3 参与试点过早并行化

**源论点**：WP3 在 WP2 冻结运行时语义之前就冻结了数据形状，造成一种“架构错觉”：契约看起来统一，但时序语义却存在分歧。

**发现：风险逻辑正确，但对 WP3 实际输出的评估不准确。**

数据形状冻结超过语义冻结这一风险确实存在。然而，temp-01 声称 WP3 仅产生“统一字段名”的说法与实现证据不符：

- WP3 的 `DiagnosticsTrace` 契约明确携带 `trace_id`、`parent_trace_id`、`chain_id`、`track_id`、`launch_request_id`、`launch_event_id`、`munition` (EngagementEntityRef)、`effects_event_id`、`damage_report_id`、`observation_packet_version` —— 这构成一个**因果链**，而不仅仅是字段名对齐。
- `test_diagnostics_trace_contract.py` 验证了所有7个链接字段在单个端到端链中与 temp-01 描述为期望 WP3-0 输出的追踪内容完全相同。
- WP3 严格限定自身范围在数据契约 —— 它未触及 `simulation_kernel.cpp` 中的 `ecs.progress()` 调用、ECS 流水线排序或调度器行为。数据形状已冻结，但运行时语义明确留给 WP4/WP5。
- WP3 从未声称冻结运行时语义；其文档将试点目标描述为“构建契约适配器和跨领域验证切片”。

建议的拆分为 WP3-0（契约追踪原型）和 WP3-1（实现试点）实际上已经发生：DiagnosticsTrace 链就是追踪原型，而空中/海军适配器就是实现试点。

**处理：风险已记录，但已通过 WP3 的领域纪律得到缓解。无需修改计划。**

### 声明4：外观有成为新上帝对象的风险

**源论点**：如果所有跨层关注点都通过 RuntimeFacade 路由，它将变成第二个单体。应拆分为会话、设置、执行、观察、诊断、参与和能力外观。

**发现：长期风险确实存在，但在当前规模过早拆分将是过度工程化。**

当前状态：
- `RuntimeFacade` 有大约30个公共方法，组织成设置、动作摄取、步骤执行、观察查询和参与导出等组。
- `RuntimeFacade::runtime()` 被明确记录为“仅用于诊断和旧适配器的兼容性逃生舱”。
- 架构测试（`test_runtime_facade_layering.py` 中的9个）强制要求维护代码不依赖逃生舱。
- `runtime_facade_contract_plan.md` 已经建议拆分为功能组。

在当前项目规模下（单个团队，一位主要开发人员），七外观拆分将增加样板代码而无法获得对应收益。拆分的触发条件应为：外观方法数量超过约40个，或出现多个独立团队需要拥有不同的外观表面。

**处理：推迟。在外观治理规则中添加拆分阈值。将建议的外观组记录为目标的拆分架构。**

### 声明5：契约分类法需要显式数据分类

**源论点**：所有东西都称为“契约”，混淆了组件、事件、视图和诊断。需要五向分类：内部状态、契约事件、契约请求、观察视图、诊断追踪。

**发现：有效的细化。架构文档中已经存在隐式区分，应使其显式化。**

架构文档（第7节）列出了16个契约族，每个都具有定义的目的和长期拥有者。内部状态（组件拥有）、事件（LaunchEvent、EffectsEvent）、请求（LaunchRequest、ActionIntentPacket）、视图（ObservationPacket）和追踪（DiagnosticsTrace）之间的区分隐式存在于拥有者分配和命名约定中。使其显式化将：

1. 防止 DTO 膨胀 —— 新字段提议需声明其所属类别。
2. 指导代码生成 —— 每个类别有不同的序列化、版本化和重放规则。
3. 简化 WP2 契约冻结决策 —— 类别决定冻结标准。

建议的规则为：
- 组件用于突变。
- 事件用于因果性。
- 数据包用于边界跨越。
- 视图用于消费。
- 追踪用于解释。

**处理：已接受。应将五类别分类作为契约治理规则加入架构基线。现有16个契约族应打上其类别标签。**

### 声明6：StateStore / EventQueue / Barrier 是概念，而非可执行规范

**源论点**：没有事件优先级族表、没有确定性的事件 ID 生成规则、没有状态分片版本递增规则、没有屏障可见性规则。没有这些，时序 DAG 仍然“高级但模糊”。

**发现：完全有效。这是识别出的最重要缺口。**

每个概念的当前状态：

| 概念 | 架构文档 | 代码 |
|---------|-----------------|------|
| StateStore | 描述为具有版本控制的权威状态，可能由宿主拥有、后端拥有或部分同步 | 不存在抽象。`flecs::world` 是唯一的权威状态，无版本控制。 |
| EventQueue | 描述为被延迟/打时间戳的事件，按 `(timestamp, priority, event_id)` 排序 | `RecentEngagementEvents` 是一个扁平的 `std::vector`，支持追加/清除，无优先级字段，无确定性排序。 |
| ClockDomain | 描述为默认嵌套触发的节奏规则 | 所有系统以单一 60Hz 运行。不存在多速率机制。 |
| Barrier | 描述为写入变得可见的一致性边界 | 不存在屏障。所有写入在 `ecs.progress()` 返回后立即可见。 |

建议的 WP2.5“调度器语义冻结”包含六个交付物（event_family_priority_table.md、state_shard_versioning_rules.md、barrier_visibility_rules.md、clock_domain_merge_rules.md、deterministic_replay_contract.md、stage_node_manifest_schema.md）是正确处方。这些都不需要代码实现——它们是约束未来实现的规范文档。

**处理：已接受。应在 WP2 和 WP4 之间插入一个调度器语义冻结工作包。这是改进当前计划中最具影响力的单项变更。**

### 声明7：GPU / 驻留状态策略需要后端配置文件和奇偶预算

**源论点**：“CPU 精确基线”如果没有显式的后端配置文件（参考、加速、驻留状态、近似）和奇偶声明将变得不可执行。

**发现：有效但优先级低于调度器语义。**

架构文档（第9节）已有明确规则：
- CPU 精确是语义基线。
- CUDA 助手通过外观/后端数据包附着。
- 设备驻留状态需要声明宿主同步、快照导出和局部视图规则的契约。
- 精确的 GPU 世界步进在奇偶性得到验证之前不被维护为替代方案。

GPU 代码被 `EF_ENABLE_CUDA_EXPERIMENTS` 门控，位于独立的 `src/gpu/` 目录下。建议的四个后端配置文件是一种有用的形式化，但不阻塞任何当前工作。

**处理：已接受，用于未来规划。应作为 WP7 交付物，而非插入到当前 WP0-WP5 序列中。**

### 声明8：验证门测试存在性而非证明性

**源论点**：门应升级为设计一致性、追踪一致性和边界一致性。WP3 的真正验收标准应是“一条 DiagnosticsTrace 可以解释完整链路”，而非“空中和海军都能产生 LaunchEvent”。

**发现：有效。当前的验收标准匹配 WP3 的有限范围，但超出该范围后应升级。**

当前网络门：
- Gate1：有 air 和 naval 的 LaunchEvent。
- Gate2：有 naval 和 diagnostics 的 ObservationPacket。
- Gate3：air 和 naval 的 DiagnosticsTrace 从 launch_request 持续到 track_observation。

WP3 文档明确将其验收描述为“建设一个同时处理空气和海军适配器的契约追踪原型”。它实现了一组基础集成，而不试图证明一个完整因果链的完整性。这是合理的范围纪律。

然而，对于 WP4/WP5，这种存在性验证是不够的。追踪一致性验证需要证明每次发射都与一次效果和至少一次观察相关联。

建议的门升级路径是合理的，但应附加到 WP4 和 WP5，而非当前 WP3 计划。

**处理：保留供参考。升级后的门应附加到 WP4 验收和 WP5 技术就绪度门中。当前 WP3 门的充分性是适当的。**

**发现：对架构文档通用关口（第11节）的批评是有效的，但WP3的具体关口已比所声称的更接近证据驱动。**

架构文档的10个验证关口确实采用了清单式风格（例如，“文档命名阶段、所有者、消耗的数据包和产生的数据包”）。然而，WP3的8个验收关口是证据驱动的：

- 关口1：“空中发射架发射和海军基座/VLS发射发出或适应相同的LaunchEvent形状”→通过 `test_air_launch_adapter.py` 和 `test_naval_launch_adapter.py` 验证
- 关口6：“DiagnosticsTrace可连接跟踪、发射请求/事件、弹药、效果、损伤和观测数据包版本”→通过 `test_diagnostics_trace_contract.py` 验证，该测试检查所有7个链接字段

temp-01要求的具体跟踪链——“谁请求发射，基于哪个跟踪快照，为什么火控接受/拒绝，弹药如何继承发射事件，引信/效果何时触发，损伤如何改变状态分片，哪个提交的快照观测读取，空中/海军差异仅在发射器/弹药/学说族中”——WP3部分验证了（第1-4项和第8项已证明；第5-7项需要调度器语义，WP3明确不涉及）。

**处理方案：应采用三级一致性模型（设计/跟踪/边界）用于WP5验证框架设计。架构文档第11节应更新以引用这些层级。**

## 5. 结论

temp-01是一份严肃且专业的架构审查。其核心诊断——“正确但过载，需要一个最小可冻结的架构内核”——是准确的。在识别的八个具体风险中：

- **一个是最具后果的发现**（声明6：调度器语义未充分规范），值得新增WP2.5工作包。
- **两个是有效的改进**（声明2和5：StageNodeManifest和合约分类），应纳入WP2/WP2.5。
- **两个是有效的长期关切**（声明4和7：外观单体和后端配置文件），可推迟处理。
- **两个部分有效但夸大**（声明1和8：过早封闭和验证关口）——现有机制比所认为的更稳健。
- **一个在逻辑上合理但对WP3产出的描述不准确**（声明3：WP2/WP3并行化风险）——WP3已交付审查所要求的合约跟踪。

推荐的WP2.5插入不会使当前WP0-WP5计划失效。它通过填补WP4开始外观硬化前最大的规范空白，从而加强了该计划。
