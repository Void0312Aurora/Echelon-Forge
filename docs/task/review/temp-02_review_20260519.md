## 1. Source Thesis

temp-02 argues that the current architecture correctly addresses "how to execute the world" (via lifecycle + DAG + contracts) but has not yet defined its highest abstraction. The project ceiling is set by what kind of system Echelon-Forge ultimately is, not by how cleanly it schedules execution nodes.

The core reframing: **DAG is a projection, not the ontology.** The real goal is a platform that unifies semantics, causality, time, information, agency, learning, and evidence — a "simulation compiler + learning platform," not merely a "runtime engine."

## 2. What to Absorb

### 2.1 SCAL as Architecture Vision

temp-02 proposes SCAL (Semantic-Causal-Agentic-Learning) as the four-face architecture framework. This is the right naming for what the architecture baseline already addresses in fragments:

| SCAL face | What it answers | Current architecture coverage | Gap |
|-----------|----------------|-------------------------------|-----|
| **Semantic** | What exists in the world? Entities, capabilities, tasks, constraints, roles, events. | P0-P10 semantic lifecycle + 9 domain model families (Section 8) + contract taxonomy (Section 7) | Domain ontology not formalized. Entity-centric rather than capability-centric. |
| **Causal** | What causes what? Which state changes produce which consequences? | Cross-layer contracts (Section 6) + event ordering (Section 5) + WP2.5 scheduler semantics | Causal graph not explicitly modeled. Causal correctness not enforced at runtime. |
| **Agentic** | Who decides? Who knows what? Who controls what? | Policy/orchestration layer (Section 6) + Command Hierarchy (P2-P4) + ActionIntentPacket + CoordinationIntentPacket | Agent = role + authority + information state + decision model + action interface not formalized. Policy still treated as monolithic. |
| **Learning** | How does the system train, evaluate, generate tasks, discover failures, improve? | Not covered by current architecture baseline. | Entirely absent. Curriculum, evaluation, capability profiling, scenario generation are all deferred to Python scripts. |

**Recommendation**: Adopt SCAL as the architecture vision statement, replacing the current "Design Thesis" (Section 1) of the architecture baseline. The four faces become the organizing framework for architecture documentation. Learning is the genuinely new face that needs design work.

### 2.2 Graph-of-Graphs: DAG as Projection, Not Ontology

temp-02 identifies seven graphs that coexist in a simulation system. Mapping to current architecture:

| Graph | Current state | Action |
|-------|--------------|--------|
| **Semantic Graph** | Implicit in model families + P0-P10 | Make explicit. This is what P0 ContentCompile produces. |
| **Causal Graph** | Implicit in cross-layer contracts + event ordering | Make explicit. WP2.5 barrier visibility is the first step. |
| **Temporal Execution Graph** | Temporal DAG (Section 5) + WP2.5 clock domain merge | Already explicit. This is the current architecture's strongest graph. |
| **Information Graph** | Implicit in sensor → track → data-link → observation chain | Elevate to first-class. See Section 2.3 below. |
| **Agency Graph** | Implicit in policy/orchestration layer + command hierarchy | Make explicit. See Section 2.4 below. |
| **Evidence Graph** | DiagnosticsTrace + validation gates + replay contract | Already has a concrete type (DiagnosticsTrace). Extend with WP2.5 replay contract. |
| **Learning Graph** | Not covered | Deferred. Requires separate architecture document. |

**Recommendation**: Add a "Graph-of-Graphs" section to the architecture baseline that positions each graph, names its owner, and declares its relationship to the other graphs. The Temporal DAG remains the execution scheduler; it is no longer presented as the architecture's defining metaphor.

### 2.3 Information State Architecture — Directly Actionable

This is temp-02's most immediately actionable contribution. The six-layer information model maps cleanly onto existing infrastructure:

```
World Truth          → flecs::world authoritative state
Sensed State         → ISensorModel::scan() → Detection / ContactList
Track State          → TrackDatabase → TrackData → TrackPacket
Shared Picture       → DataLinkSystem → shared tactical picture
Agent Observation    → AgentObservation / ObservationPacket
Decision Belief      → [MISSING — currently observation maps directly to action]
```

The current architecture has layers 1-5. Layer 6 (Decision Belief) is the critical missing piece — its absence is why RL policies can learn "god's-eye-view" strategies. Introducing an explicit belief layer would:

1. Prevent policies from consuming world truth directly.
2. Enable partial observability, communication constraints, and sensor deception as first-class simulation features.
3. Make information degradation (latency, drop, fusion, inference) architecturally visible rather than buried in system implementations.

**Recommendation**: Add Information State Architecture to the architecture baseline as a new section. Define the six layers, their ownership, and the transformation rules between them. Make `DecisionBelief` a formal concept in the ObservationViewSpec contract — an observation is what the agent sees; a belief is what the agent thinks is true.

### 2.4 Agent Model — Role + Authority + Information + Decision + Action

temp-02's agent decomposition into five layers maps naturally onto the existing P2-P4 command hierarchy:

```
Strategic / Operational Intent   → P2 TaskingIntent (TaskOrder, LeaderIntent)
Tactical Doctrine                → DoctrineFamily (Section 8)
Platform Autonomy                → P4 PlatformControl
Control / Autopilot              → P4 force/torque outputs → P5 PhysicsStep
Policy Network                   → Pluggable at any layer
```

The key insight: **RL policy is not the agent. It is a replaceable decision model inserted at one or more layers of the agent hierarchy.** The five-element agent definition (role + authority + information state + decision model + action interface) should replace the implicit "agent = neural policy" assumption.

**Recommendation**: Formalize the agent model in WP4-D (Policy And Coordination Bridge). Define `AgentRole` as a contract type with fields for role, authority scope, information state source, decision model reference, and action interface. This enables future support for scripted doctrine, rule-based tactics, RL policies, LLM planners, MCTS, and human-in-the-loop — all through the same agent interface.

### 2.5 Capability Graph — Platform = Capability Bundle

The entity-centric model (`spawn_unit("F-16C_Block50")`) is the root cause of potential air/naval/weapon divergence. A capability-centric model defines platforms as compositions:

```
Platform = mobility_capability
         + sensor_capability
         + communication_capability
         + launcher_capability
         + survivability_capability
         + command_capability
         + doctrine_profile
```

This is the true architectural prevention against vertical stacks. A new domain (ground, space, submarine) adds capability implementations, not a new runtime path.

**Recommendation**: Add capability composition to the domain extension model (Section 8). Define `Capability` as a contract concept with typed interfaces. Keep the current `spawn_unit(type_name)` as a convenience shortcut that expands to capability composition internally. The long-term target is `spawn_platform({capabilities...})` as the canonical creation path.

### 2.6 Simulation Compiler — Long-Term Positioning

The compilation pipeline (Scenario → Semantic Compilation → Causal Dependencies → Temporal Schedule → Runtime → Evidence → Learning) is the correct long-term vision. It reframes Echelon-Forge from "a simulator that runs scenarios" to "a platform that compiles task semantics into executable, explainable, comparable experiments."

This is not actionable at the current WP0-WP5 stage — a compiler needs a verified runtime first. But it should be stated as the project's long-term architecture vision to prevent the current kernel work from being mistaken for the final architecture.

**Recommendation**: Add "Simulation Compiler" as the architecture vision statement. The current WP0-WP5 work builds the verified runtime kernel that the compiler will target.

## 5. Architecture Vision Statement (Proposed)

Replace the current architecture baseline Section 1 ("Design Thesis") with:

> Echelon-Forge is a **semantic-causal simulation compiler and learning platform**. It compiles task semantics, domain models, agent structures, and fidelity requirements into executable, explainable, replayable, and comparable simulation experiments.
>
> The architecture is organized around four faces:
>
> - **Semantic** — What exists in the world. Domain ontology, capability graph, scenario and mission semantics.
> - **Causal** — What causes what. Causal graph, temporal execution DAG, event model, state transition semantics, counterfactual model.
> - **Agentic** — Who decides and acts. Agent role model, command hierarchy, information state architecture, decision layering, policy interface, doctrine model.
> - **Learning** — How the system improves. Curriculum architecture, world model architecture, evaluation architecture, capability profiler, scenario generator.
>
> The Temporal DAG is the execution projection within the Causal face — it schedules computation, but it is not the architecture's defining abstraction. The architecture's ceiling is set by how well these four faces cohere into a unified platform, not by how cleanly the DAG is implemented.

## 6. Conclusion

temp-02 is the correct next conversation after the scheduler semantics and facade alignment reviews. It does not identify gaps in the current architecture — it identifies that the current architecture is the kernel of a larger system that has not yet been named.

The four most valuable contributions to absorb:

1. **SCAL** as the organizing framework — replaces the flat "Design Thesis" with four faces that each have clear ownership and deliverables.
2. **Information State Architecture** — the six-layer model is directly actionable and addresses the single biggest RL quality risk (god's-eye-view policies).
3. **Agent = role + authority + information + decision + action** — prevents the architecture from locking into "agent = neural policy" as RL methods evolve.
4. **Capability Graph** — the true architectural prevention against air/naval/weapon vertical stacks.

The SCAL vision does not invalidate the current WP0-WP5 plan. It gives that plan a name and a ceiling.
