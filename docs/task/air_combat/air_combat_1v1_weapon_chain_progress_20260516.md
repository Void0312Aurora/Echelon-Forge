## 1. Document Positioning

This document records the actual progress made in the current iteration around the `1v1` air combat first phase.

The goal of this iteration is not to connect a full training entry, but first to answer a more fundamental question:

1. Whether `fire_missile()` in the current kernel can serve as the real engagement chain starting point for `1v1`.
2. Whether the current missile chain has basic anomalies that would directly block `1v1`.
3. What `1v1` subsequent contracts should treat as "established" and what should continue to be treated as blockers.

## 2. Newly Confirmed Facts in This Iteration

### 2.1 The basic launch contract of `fire_missile()` is now verifiable via regression

Current focused runtime tests have proven:

1. Without a valid enemy track, `fire_missile(attacker_id, target_id)` does not launch.
2. With a valid enemy track present, `fire_missile()` successfully spawns a missile entity.
3. After launch, `missiles_remaining` is decremented.
4. After launch, a `WeaponCooldown` is entered; consecutive launches are not possible before cooldown expires.

Corresponding test file:

- [test_air_combat_1v1_fire_missile.py](../../../tests/runtime/test_air_combat_1v1_fire_missile.py)

### 2.2 Two weapon chain issues that directly blocked `1v1` were fixed in this iteration

Two key issues were confirmed and fixed at the kernel layer in this iteration:

1. Missile seeker/guidance candidate targets did not exclude the launcher and same-side targets.
2. Missile entities generated by `fire_missile()` did not have the `Mass` / `ForceAccumulator` required for translational integration, and the repository mainline had already deprecated the old `UpdatePosition`, causing missiles to almost never enter the real translation chain.

After fixes:

1. Missiles no longer re-acquire the launcher as a guidance lock target.
2. The original detection layer of the missile seeker no longer includes same-side targets.
3. Missiles now enter the currently maintained leapfrog translational integration chain, rather than only modifying `Velocity` while barely moving forward.

### 2.3 A real kill chain has formed under the current `head-on` fixture

Under the current maintained fixture:

## 3. Freezable 1v1 Phase 1 Contract

Based on the results of this iteration, the weapon chain contract for Phase 1 of `1v1` can be frozen as follows:

1. Phase 1 allows directly using `SimulationKernel.fire_missile()` as the real launch main chain.
2. Phase 1 kill / splash determination can be based on:
   - `is_unit_active(target_id) == false`
   - or target `health <= 0`
3. Phase 1 can treat "Blue aircraft alive and Red aircraft destroyed" as the minimal win sample.
4. Phase 1 is still safer to host training tasks on the `execution` mainline; there is no need to switch to `cooperative_execution` yet.

## 4. Parts Still Not Connected

Although the weapon chain has advanced significantly compared to the previous iteration, the following parts are still not connected by this iteration's work:

1. `PilotAction.fire_weapon / master_arm / weapon_select_id` are still not directly connected to the maintained missile launch main chain.
2. The `ScenarioLoader` / `execution` mainline still does not have maintained `1v1` termination reasons and reward contracts.
3. Current `1v1` still lacks an independent eval JSON result metric.
4. There is still no maintained scripted red side / frozen opponent interface.

Therefore, the conclusion of this iteration is not "`1v1` training is complete," but rather:

1. The real weapon kernel closed loop for `1v1` is established.
2. Subsequent work can proceed to freeze reward / termination / eval contracts, rather than remaining in the uncertain stage of "whether it can actually engage."

## 5. Suggested Next Steps

The most suitable next step is now clearer than in the previous iteration:

1. First add explicit `1v1` termination contracts:
   - Blue wins
   - Red wins
   - Both destroyed
   - Timeout
   - Ammo depleted unresolved
2. Then connect that contract to the reward / done / info output of the `execution` mainline.
3. Then supplement a minimal `1v1` eval metric, at least outputting win/loss, timeout, termination reason, and engagement steps.
4. Finally consider scripted red side or frozen opponent – do not reverse the order.
