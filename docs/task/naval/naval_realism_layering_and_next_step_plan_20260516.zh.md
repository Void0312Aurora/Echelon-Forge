## 一、当前场景结论

当前海战主线不是“真实交战场景”，而是一个已经可运行、可验证的“最小现实海上屏护接触场景”。

当前场景的核心语义是：

1. 蓝方主战舰 `DDG-51` 作为屏护舰。
2. 蓝方 `T-AKE-1` 作为被护高价值辅助舰。
3. 红方为一个敌对水面接触目标。
4. 当前主要验证的是“发现-共享-报告”链路，而不是武器交战。

这条线的价值在于，它已经从真实舰型、真实公开参数、合理接触几何出发，建立了一条最小但不虚假的海上战术样例。

## 二、现实性分层清单

### 2.1 已可信的现实基线

以下部分可以视为当前主线中“已可信”的现实基线：

1. **舰型选取真实**
   - 蓝方屏护舰使用 `USS Arleigh Burke (DDG-51)`。
   - 蓝方被护舰使用 `USNS Lewis and Clark (T-AKE-1)`。
   - 二者都来自现实中可公开追溯的舰型与平台资料。

2. **公开参数已落库**
   - 长度、型宽、吃水、排水量、最大航速、经济航速、航程、编制等字段已经进入 `ShipPlatform`。
   - 参数换算和来源已在 [ship_unit_references.md](/home/void0312/Workshop/CMO/docs/standards/naval/ship_unit_references.md) 说明。

3. **任务关系真实且克制**
   - 当前不是凭空发明“海上 dogfight”，而是从“驱逐舰屏护补给舰”这种现实里常见、语义明确的护航关系切入。
   - `TASK_SCREEN` / `TASK_SUPPORT` 的最小海军任务映射已经建立。

4. **接触几何合理**
   - `DDG-51` 位于 `T-AKE-1` 前方约 `8 nmi`。
   - 红方接触位于 `DDG` 可先发现、但 `HVU` 起始局部雷达尚不可先发现的位置。
   - 这使“屏护舰先见敌、被护舰靠共享态势获知接触”成为自然结果，而不是测试硬编码。

5. **传感器范围采用保守现实约束**
   - 当前 `AN/SPS-67(V)` 与辅助舰导航雷达的作用距离，不是凭空写入大数值，而是按雷达地平线/视距近似建立保守上限。
   - 这比把水面雷达写成一个缺来源的大范围探测器更可信。

6. **共享态势链路已打通**
   - 当前运行时已经能验证：`DDG` 本舰发现 -> `HVU` 共享航迹 -> `HVU` 接触报告。
   - 运行时测试和合同测试均已通过。

### 2.2 可接受的诚实简化

以下部分还不算高保真，但当前阶段属于可以接受的诚实简化：

1. **舰船运动为平面运动学**
   - 当前舰船会在水面平动、限速、自动更新航向。
   - 没有海况、惯性转弯、加减速响应、推进系统时滞等更高阶操纵细节。
   - 这足以支持“最小接触场景”，但不足以支持真实舰艇机动对抗。

2. **雷达探测为简化概率模型**
   - 当前探测考虑距离、视场、噪声、扫描周期等因素。
   - 但尚未建立舰船级 RCS、海杂波、海况、模式切换、识别链等更完整的现实因素。

3. **数据链为最小共享模型**
   - 当前共享机制已考虑同 side、同网络、距离与 LOS 限制。
   - 但网络组织仍是阵营级近似，不是现实舰队 C2 / Link 管理模型。

4. **命中盒与系统区段是结构化占位**
   - 当前舰船已有分区 hitbox 和系统列表。
   - 这为后续抗毁/毁伤细化留了结构，但现阶段还不能代表真实舰体抗毁能力。

### 2.3 当前已知失真点

以下部分是当前场景里最应该明确标注的失真点：

1. **红方舰型尚未真实选定**
   - 当前红方是敌对接触语义，但运行时仍复用 `T-AKE-1` 舰体配置做占位。
   - 这意味着红方目前不是一个真实敌舰模型。

2. **舰船血量模型不具现实解释力**
   - `health` 目前按“每吨约 1 HP”近似。
   - 这只能避免完全空白，不能解释真实抗毁、毁伤传播、任务失能与沉没过程。

3. **武器系统尚未进入可信阶段**
   - `VLS`、舰炮、`CIWS`、反舰导弹、防空导弹都还没有以可信方式进入运行时战斗链。
   - 当前 metadata 中记录的装备，不应被误读为“已经实现”。

4. **数据链配置与现实编组不一致**
   - 当前工厂按阵营自动分配数据链网络号。
   - 这适合最小共享态势，但不等于真实编组、频段、节点角色、链路可靠性建模。

5. **任务语义先于护航控制**
   - 当前已有 `TASK_SCREEN` 语义，但还没有成熟的动态 screen-keeping 控制逻辑。
   - 也就是说，现在更像“挂上护航关系的几何样例”，而不是“真实可操作的护航战术控制器”。

### 2.4 当前明确不应误称为“真实海战”的部分

为了避免后续语义漂移，当前以下表述应明确避免：

1. 不应把当前场景称为“真实海战交战场景”。
2. 不应把红方占位舰体称为“已完成的敌舰建模”。
3. 不应把当前 `health`、generic damage 或 metadata 武器记录称为“舰艇作战级毁伤/武器仿真”。
4. 不应把当前数据链共享直接表述为“真实舰队战术数据链体系已完成”。

更准确的表述应是：

- **最小现实海上屏护接触场景**
- **护航/发现/共享态势基线**
- **进入武器与抗毁建模前的海战启动样例**

## 三、当前场景的下一步计划安排

### 3.1 总体原则

当前阶段先不继续扩展实现，而是冻结下一步的收敛方向。

下一步的目标不应是：

1. 直接进入舰艇武器交战。
2. 直接做完整护航控制器。
3. 直接引入真实红方编队、电子战、毁伤和多舰协同。

下一步应保持在“当前场景自然延长一小步”的范围内。

### 3.2 建议的下一步

建议下一步冻结为：

**在现有 `DDG-51` 屏护 `T-AKE-1` 场景上，建立一个“红方接触逼近 / 最近通过距离”变体，并补一条对应合同。**

理由：

1. 这一步仍然停留在“接触管理”和“屏护几何”层，不会虚假跳入尚未可信的武器作战。
2. 它可以直接检验当前最小场景是否只会“静态摆拍”，还是已经能承载基本海上态势演化。
3. 它为后续是否需要动态 screen-keeping 控制提供明确判断依据。
4. 它不要求现在就解决红方真实选型、武器链、毁伤链这些更大的问题。

### 3.3 下一步的冻结工作包

下一步只冻结两个很窄的工作包：

1. **WP-N1：逼近场景变体**
   - 在现有场景基础上，让红方作为敌对水面接触向蓝方支援舰方向逼近。
   - 保持蓝方 `DDG` 与 `HVU` 的现实基线不变。
   - 暂不引入武器与交战逻辑。

2. **WP-N2：最近通过距离合同**
   - 为该场景增加 focused contract。
   - 核心检查项是：
     - `DDG` 仍应先获得本舰接触；
     - `HVU` 应通过共享态势获知接触；
     - `HVU` 与红方的最近通过距离应满足预设阈值；
     - 当前若无动态控制，则合同应诚实反映“现状只是初始几何维持，而非主动护航机动”。

### 3.4 当前明确暂缓的事项

下一步计划中，以下事项明确暂缓：

1. 真实红方舰型库扩充
2. 舰艇武器、VLS、舰炮、`CIWS` 发射链
3. 舰艇毁伤、失能、沉没与任务失效链
4. 动态 screen-keeping 控制器
5. 多舰编队护航或更复杂海战战术

原因不是这些不重要，而是当前最需要先确认：

**现有最小场景，能否稳定承载“接触逼近 + 几何约束 + 共享态势”这一层。**

## 五、当前冻结结论

当前海战主线的正确定位是：

1. 它已经不是空壳，而是一个可验证的最小现实海上屏护样例。
2. 它已经建立了真实舰型、合理接触几何与共享态势链路。
3. 它还没有进入可信的海上武器交战层。
4. 它的下一步不应跳进完整海战，而应先做“逼近接触 / 最近通过距离”这一层的收敛验证。

本结论冻结到下一次明确重开海战推进前为止。
