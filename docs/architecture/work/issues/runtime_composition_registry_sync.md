## Scope

This issue owns every surface that records *what the simulation composes* and had
fallen behind the component registry: the executable-graph census pin in the evidence
tool, the generated profile projection, evidence and migration-closure artifacts, the
host/batch semantic reference, the Cordis compatibility bundle, and the test literals
that pin the same census.

It excludes:

- the ground damage mechanism itself, which stays with its own package;
- the pre-existing governance, structural-boundary and diagnostics failures listed
  under [Residual Issues](#residual-issues), which were reproduced on a tree that does
  not contain this work;
- the decision to widen the CI push trigger, which needs a known-failure baseline
  strategy and is deliberately not taken here.

## Root Cause

The registry constructs **85 components** and **34 systems**. The census evidence of
record is the archived
[kernel census](../archive/cordis_simulation_composition_kernel/cordis_simulation_composition_census_20260817.md),
which states "83 component registrations, 34 active system registrations" and whose
owner is `architecture/runtime-composition`. That package was archived by `4fb35eb2`
on **2026-08-17**, and no live document carried the owner again until this one.

`10945ffc` on **2026-09-21** added two components —
`GroundPlatformDamageState` and `NavalCommandIntent` — and updated the requested and
resolved manifests to match. It carried a `wip(domain-mech)` message prefix, sits only
on `work/domain-mechanisms`, and **is not an ancestor of `main` or `origin/main`**. The
commit stopped at the manifests. Everything derived from them was left behind.

Two conditions therefore overlapped: the concern had no live owner for thirty-five
days, and the branch carrying the change has never been watched by a gate.

failure unable to tell what the registry had grown to.

## Why No Gate Caught It

The evidence gate exists and was red the whole time:
`runtime_composition_evidence_contract.py check` reported
`ContractError: evidence.registry_drift@$`. It had simply never run on this branch.

[`ci-smoke.yml`](../../../../.github/workflows/ci-smoke.yml) triggers on pushes to
`main` and `master` and on pull requests. This branch has never been a pull request, so
the workflow has produced no jobs for it. The gate was unwatched, not absent.

## Repair Order

The order is causal, not stylistic, and it is longer than it first appears. The tool
refuses the new census; the projection feeds the evidence; the Cordis producer re-derives
the projection and seals provenance over it; the host/batch capture joins live native and
Python hosts to that projection; and the closure requires all of them.

1. Repair the census pin to 85, preserving its tripwire semantics.
2. Regenerate the profile projection.
3. Re-pin the Cordis bundle's stale artifact hashes, then the package descriptor's bundle
   hash.
4. Run the Cordis producer, which re-derives the projection independently and seals the
   provenance and diagnostics artifacts.
5. Refresh the provenance and diagnostics fixtures from the producer output.
6. Rebuild the parity probe, the Cordis conformance binary, and `ef_py`.
7. Capture host/batch parity evidence, refreshing the frozen semantic reference.
8. Regenerate the migration closure.
9. Update the test literals.

## Repair Record

Measured on the Windows MSVC host at the revision that carries this record.

**Cross-implementation agreement.** Step 4 is the strongest evidence that the
regeneration was correct rather than merely self-consistent. The producer lowers the
profile projection from the manifests in JavaScript and requires the result to equal the
checked-in fixture. It accepted the regenerated projection, so an independent
implementation reproduces it.

**Three findings that the inventory above did not predict:**

- The producer could not run at all before the repair. It failed at
  `bundle artifact hash mismatch` because the bundle pins its own inputs. The Cordis half
  of the composition was broken, not merely stale, and had been since `10945ffc`.
- `ef_py` had to be rebuilt. The extension compiles the executable-graph hash in, so
  refreshing only the fixtures produced
  `ParityError: Python semantic composition evidence unavailable: composition_evidence.runtime_identity_mismatch`.
  A rebuild of the parity binaries alone was not sufficient.
- Entity identifiers in the parity workload shifted, because the number of registered
  components changes how the ECS allocates entity handles. The frozen semantic reference
  therefore had to be refreshed. This is gated rather than trusted: `capture` verifies
  native-to-Python semantic agreement *before* refreshing, and re-checks both hosts
  against the refreshed reference afterwards.

**Acceptance.** The prediction was that the composition suite would reach
`0 failed, 70 passed, 3 skipped, 0 errors` from a baseline of `8 failed, 53 passed,
3 skipped, 9 errors` at `b74e100a`.

```
before:  8 failed, 53 passed, 3 skipped, 9 errors
after:   0 failed, 72 passed, 1 skipped
```

Both rows are **73** collected tests, `8+53+3+9 = 73` and `0+72+1 = 73`. The arithmetic
is written out because a review mis-summed the before row to 74 and a later reader
should not have to recheck it.

The prediction was met and exceeded: two tests that had been skipping now run and pass,
because the native probe, Node and the Cordis dependencies are present — the same
absence that hid the defect also hid its verification. The change is not attributable to
this issue's surfaces alone, so the evidence is that the set is empty rather than that
the count fell.

An independent review measured the before row as `8 failed, 52 passed, 4 skipped,
9 errors` on the parent commit, one skip higher. The difference is the Cordis-dependency
skip, which is the environment dependence this record already discloses. The before row
above is the one measured on the host that carried the work; neither row is portable
across hosts that differ in the Cordis dependencies.

**A pure re-record.** No runtime *logic* moved:

```
git diff --stat -- src/core src/systems src/runtime/facade src/models   # empty
```

That set is not sufficient on its own, and a review was right to say so.
`src/runtime/contracts/composition/runtime_composition_evidence.v1.generated.h` sits
outside it and is consumed by
`src/runtime/facade/runtime_facade_composition_evidence.cpp`, so the runtime's **reported
composition identity** did change. That header carries the executable-graph and profile
projection digests, it is why `ef_py` reported `runtime_identity_mismatch`, and it is why
the host/batch capture had to be re-run rather than re-recorded.

The distinction that carries the claim is logic versus identity. The generated header is
one of the recorded surfaces listed in the inventory, so its change is the debt being
re-recorded, not a behaviour edit. No hand-written runtime source moved.

Outside generated artifacts and raw-byte pins, the diff is the census pin and the test
literals in the inventory. Regenerating the projection a second time reproduces
byte-identical artifacts.

**Gates.** Governance, structural boundaries and the ground suites show the same
pre-existing failure sets they showed before this work, with no arrivals; the
documentation link audit reports 0 issues across 199 documents; the Cordis package tests
pass 20 of 20; `ruff` is clean.

## Gate Coverage

The projection tool exposed `generate` and `validate` but no way to ask whether the
recorded state still matched the registry, so nothing could police it. This issue adds a
`check` mode and wires it between the manifest check and the evidence check.

`check` and `generate` share one `expected_artifacts()` function, so the guard cannot
drift from the generator it polices. Its reach is narrower than "registry drift", and an
independent review was right to narrow that: the projection tool reads no registry at
all. Its inputs are the composition fixtures, so it is blind to a pure registry change and
cannot fire on one alone.

What it does catch is the shape that actually occurred — a change that reaches the
manifests and then stops. The registry-to-manifest binding is enforced elsewhere, by the
component census assertion in
[the composition contract test](../../../../tests/architecture/composition/test_simulation_composition_contract.py)
and by the census pin in the evidence tool. The value added here is against a regeneration
cascade that halts halfway: a recorded surface that no command asks about is how the
projection, evidence, closure and host/batch reference all stayed at the previous census.

Until the push trigger is widened, that step does not execute in CI. It is recorded here
as inert rather than presented as coverage: a step that cannot run is not a gate. The
capability still earns its place because the same command is the regression tripwire for
this defect class on a build host.

## Provenance

The debt was found by the ground systems-owner package while pursuing a separate ground

The transfer is explicit in both directions: the ground package names this issue in its
acceptance record, and this issue names the ground package as its origin.

## Residual Issues

Pre-existing failures reproduced on a tree without this work, attributed to commits
`9d9c8aae`, `13c73a10` and `33f54dfd`, and not owned here:

- `test_archive_retirement` — twenty documents under `docs/architecture/work/archive/`
  are unregistered, and the guard hardcodes a retirement date of `2026-08-13`;
- `test_owner_local_work_and_reviews_declare_minimum_metadata` on
  `docs/systems/effects/reviews/continuous_rod_component_load_admission_20260914/`;
- `test_diagnostics_top_level_sprawl_never_grows` — fifteen `kill_chain_*` tools;
- two binding-quarantine boundaries under `tests/architecture/structural_boundaries/`.

Two gaps this repair leaves open, neither blocking:

- The five bundle artifact pins are only exercised through `npm run produce`
  ([`cli.mjs`](../../../../packages/cordis-runtime/src/cli.mjs) `readBundleArtifact`).
  The Node tests cover only the descriptor-level `profile.bundle` pin, so a stale bundle
  pin is invisible to `npm test` and surfaces only when someone regenerates.
- A document that is untracked during local verification is invisible to every census
  guard that enumerates through `git ls-files`, including the tier census this record had
  to refresh. "The governance suite is unchanged" is therefore not a claim that can be
  made before the new document is staged. The first revision of this record made exactly
  that mistake and an independent round caught it.

The CI push trigger remains closed. Opening it would expose every pre-existing failure
above at once, so it needs a known-failure baseline before it can be a gate rather than a
wall of red.

**What this branch actually re-ran.** Steps 1–2 (census pin, projection, evidence) were
already done by `3ea5c184`, `b8cd32d3` and `6830414e`. The Cordis half and everything
downstream were not, so the producer failed with `bundle artifact hash mismatch`, the same
finding as the original record. Steps 3–9 were redone:

- re-pinned the bundle (projection, requested and resolved manifests) and the descriptor;
- ran the producer and adopted its provenance and diagnostics;
- rebuilt the native probes and `ef_py`;
- recaptured the host/batch parity and the semantic reference (entity id `581 → 583`, no
  kinematic value moved);
- regenerated the closure. It adds one caller, `python/rl/ground/native_probe.py`, under
  `simulation_kernel.default_compatibility`;
- updated the `producer.test.mjs` projection literal.

**Residuals specific to this branch:**

- The frozen host/batch semantic reference pins Flecs-allocated entity ids. Every census
  change forces a refresh. Removing that dependence belongs with
  [Stable Entity Identity For Stochastic Draws](stable_entity_identity_for_stochastic_draws.md).
- The recaptured parity timings are about 2x the previous capture on a loaded host. The
  budgets pass with wide margin, but the baseline is not a trend reference and should be
  recaptured on a quiet host before anyone reads it as one.
- The closure admitted `native_probe.py` under the generic compatibility disposition. Its
  real disposition is the `native_probe_only` quarantine enforced by the WP22-E Ground
  native-probe allowlist. The closure tool has no fail-closed guard for new Python callers.
